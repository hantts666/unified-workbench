# 登录与权限完善（2026-10-28）

用户授权及增量验收见 `specs/002-auth-permissions/spec.json`。V0.2 的 `SPEC-001` 与其证据保留为历史基线，不改写历史执行结果。当前新增接口契约为 `contracts/platform-v03.openapi.json`。

## 本轮行为

- 登录使用账号和来源地址两个持久化窗口，分别为每 15 分钟 10 次、120 次。原子计数阻止并发绕过；同账号成功登录清除账号失败计数。错误凭据和停用账号返回同一提示。限流响应带 `Retry-After`。
- 只信任部署中单层网关覆盖的来源地址。平台 API 不公开端口；网关覆盖客户端提交的 `X-Forwarded-For`。Origin 必须匹配入口协议与主机，内部鉴权使用独立服务凭据。
- 新建/重置账号必须先换密，已有账号不被强制重置。受限会话只能访问本人信息、密码及会话操作；财务内部鉴权也拒绝业务授权。密码修改校验当前密码、长度与不同于旧密码，并撤销所有会话。界面另验证确认密码。
- 登录和密码重置对同一用户行进行锁定和条件更新，防止重置提交之后旧密码请求留下有效会话。会话仅存随机令牌摘要，设备页面使用不可认证的独立 UUID。最长 8 小时、最多 10 个有效登录。
- 用户维护权限不能重置、启停、解锁或退出权限超出操作者范围的账号，授权管理员可以执行上述管理。只有角色维护权限时，不能改变已分配角色的权限或状态，防止通过已拥有的角色自我提权。
- 始终保留一个具备全部六项平台管理权限的有效账号。授权管理员可以分配财务权限，但本身不隐式拥有财务数据访问权限。
- 移除公司成员资格会同时删除该公司角色；重新加入不恢复旧角色。成员移除与角色分配使用可串行化事务，冲突时返回可重试提示。
- 实际生效权限由服务端计算。服务端逐请求校验，前端在授权操作、窗口焦点变化或 30 秒内检查后更新并卸载失效应用。

## 运行验收

只在独立 PostgreSQL schema 中运行测试，避免对在线账号和角色执行验收写入。

```sh
# Windows PowerShell: $env:PLATFORM_TEST_SCHEMA='auth_test_20261028'
export PLATFORM_TEST_SCHEMA=auth_test_20261028
node scripts/prepare-auth-test.mjs
npm run db:generate
npm run typecheck
npm run build:portal
npm run build:sample
npm run test:auth-security
npm run test:auth-security-browser
```

真实部署验证另用 `DEPLOYED_TEST_BASE` 和私有账号文件运行 `npm run test:auth-security-deployed`。报告只保存时间、检查结果和代码指纹；不保存密码、Cookie、原始账号或单据。

将本轮三个报告脱敏复制到 `evidence/reports/` 后执行 `npm run auth:delivery-check`，验证报告对应当前实现且覆盖全部要求。

## 部署顺序

1. 先备份独立测试平台数据库及运行版本。新迁移只新增字段、索引和登录计数表，保留所有旧用户、角色、公司和财务数据。
2. 应用 `202610280001_auth_security` 平台迁移，再部署通过验收的应用镜像。新建 schema 的默认授权需使平台应用账号能读写新表。
3. 检查两项健康端点版本、登录与受限账户流程、旧入口及 11 个容器，再推送验收证据。
4. 旧镜像不包含本轮强制换密保护，不应直接退回旧安全行为。已有回滚工具会拒绝 schema 不同的版本；出现问题优先修正应用并保留数据库。

正式 TLS、外部 SSO、短信/邮件找回密码和 MFA 未纳入本轮，不影响现有试用账号登录。
